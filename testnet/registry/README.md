# Testnet Contract Registry

## Overview

This directory (`testnet/registry/`) serves as a lightweight, integrator-facing mirror of **"what's live on testnet right now"**. It is explicitly a **read-oriented companion** to (not a replacement for) the excluded `deployments/testnet.json`.

## Purpose

| This Registry (`testnet/registry/`) | Deployments Artifact (`deployments/testnet.json`) |
|---|---|
| Human-readable documentation | Machine-readable deployment output |
| Curated by maintainers | Generated by deploy script |
| Explains status, caveats, procedures | Records contract IDs, WASM hashes |
| Updated manually after verification | Updated automatically by deploy pipeline |
| Includes operational runbooks | Pure data |

## When to Update This Registry

| Trigger | Action |
|---|---|
| Contract deployed to testnet | Update `contract-status.md` + `last-verified.json` |
| Contract upgraded | Update `upgrade-history.md` + `wasm-hash-reference.md` |
| Health check performed | Update `last-verified.json` timestamp |
| Admin/controller address changed | Update `admin-addresses.md` |
| New known test account created | Update `known-test-accounts.md` |
| Incident investigated | Add findings to relevant runbook |

## Relationship to `deployments/testnet.json`

```
deploy.sh (or CI)
       │
       ▼
deployments/testnet.json  ───►  testnet/registry/ (manual curation)
       │                            │
       │ Raw deployment output      │ Human-readable + procedures
       │ Contract IDs, WASM hashes  │ Caveats, runbooks, verification
       ▼                            ▼
   Source of truth            Integrator reference
```

**Update Process**:
1. Deploy script writes `deployments/testnet.json`
2. Maintainer verifies contracts using `verify-contract-live.md`
3. Maintainer updates `testnet/registry/` files with verified data
4. `last-verified.json` updated for automated staleness checks

## Automated Staleness Detection

A future CI job/bot can:
1. Read `last-verified.json`
2. Check if any contract timestamp > 30 days old
3. Alert maintainers to re-verify

```json
// last-verified.json format
{
  "ephemeral_account": "2026-09-24T00:00:00Z",
  "sweep_controller": "2026-09-24T00:00:00Z",
  "reserve_contract": "2026-09-24T00:00:00Z",
  "account_factory": "2026-09-24T00:00:00Z"
}
```

## For Integrators

Start here:
1. **Check status**: `contract-status.md` - what's deployed?
2. **Get contract IDs**: From `contract-status.md` table
3. **Verify health**: Run `verify-contract-live.md` procedures
4. **Subscribe to events**: Use `event-topics.md` for indexer filters
5. **Handle errors**: Consult `runbooks/` for failure scenarios

## For Maintainers

Workflow:
1. Deploy contracts (updates `deployments/testnet.json`)
2. Verify each contract (`verify-contract-live.md`)
3. Update `contract-status.md` with IDs, WASM hashes, caveats
4. Update `last-verified.json` with current ISO timestamp
5. Update `wasm-hash-reference.md` with commit→hash mapping
6. If upgraded, log in `upgrade-history.md`

## Refresh workflow: registry vs deployments/testnet.json

The registry follows `deployments/testnet.json`; it never leads it. `deployments/testnet.json` is the machine-readable output of `scripts/deploy-testnet.sh` (its committed copy has `deployedAt` `2026-10-10T04:38:14Z`). Every ID and hash recorded in these docs is copied *from* that file after an on-chain check - never invented here.

### Which file is authoritative for what

| Question | Authoritative source | Notes |
|---|---|---|
| What are the current contract IDs, WASM hash, and deploy time? | `deployments/testnet.json` | Generated by the deploy script; overwritten on every redeploy and invalidated by testnet resets. |
| Which contracts are part of the supported testnet deployment? | `README.md` + `testnet/docs/overview.md` + this registry | Only `ephemeral_account` and `sweep_controller` are supported; the other two IDs in the JSON are not deployed by the tooling. |
| Is a given ID live and returning sane values right now? | Manual run of `verify-contract-live.md` against RPC | The registry records the result; it does not make the result true. |
| When was a contract last checked? | `last-verified.json` | Machine-readable timestamps consumed by staleness checks. |
| What caveats, gaps, and runbooks apply? | `contract-status.md` and the per-contract / runbook files | Curated human-readable prose. |

### Step-by-step refresh procedure

1. **A deploy or reset happens.** `scripts/deploy-testnet.sh` rewrites `deployments/testnet.json` with fresh IDs and `deployedAt`. Registry editors do **not** touch that file.
2. **Read the new record.** Copy the IDs and `deployedAt` from `deployments/testnet.json` (read-only).
3. **Verify on-chain.** Run the manual health check in `verify-contract-live.md` (the "Copy-paste health-check script" section) against those IDs using RPC `https://soroban-testnet.stellar.org` and passphrase `Test SDF Network ; September 2015`.
4. **Update status prose.** Edit `contract-status.md` (quick reference and detailed sections) with the verified IDs, dates, and caveats. Keep the discrepancy note intact: the JSON lists four IDs while the README/overview support only two.
5. **Record the timestamp.** Set the ISO-8601 UTC timestamp in `last-verified.json` for each contract actually verified; keep all existing keys and add new ones only when a new contract is introduced.
6. **Sync code metadata.** If the deployed WASM changed, update `wasm-hash-reference.md` and `upgrade-history.md`.
7. **Commit only the docs.** Stage the `testnet/registry/` (and related `testnet/config/`) changes. Do not stage `deployments/testnet.json` in a registry refresh.

### Rule for this batch: do not edit `deployments/testnet.json`

This documentation batch is strictly read-oriented with respect to `deployments/testnet.json`. Do not create, modify, or "fix" that file here - it is owned by `scripts/deploy-testnet.sh` and is **off-limits** for this batch. If the committed file appears inconsistent with the prose (for example, it lists all four contract IDs while the README and overview say only two are part of the supported deployment), record and explain the discrepancy in the registry prose rather than editing the JSON. Contract IDs change on every redeploy and testnet reset; the registry documents them, it does not define them.
